## 📋 文档信息

### 文档目的

本文档为 7zi 项目制定完整的灾难恢复 (Disaster Recovery, DR) 和业务连续性计划 (Business Continuity Plan, BCP)，确保在发生系统故障、数据丢失或服务中断时，能够快速恢复服务并最小化业务损失。

### 适用范围

- **主要服务**: 7zi.com 网站及相关服务
- **测试环境**: bot5.szspd.cn
- **服务器集群**: 计划中的 8 台服务器集群
- **数据资产**: 用户数据、应用代码、配置文件、日志等

### 关键术语

- **RTO (Recovery Time Objective)**: 恢复时间目标 - 从灾难发生到服务恢复可接受的最大时间
- **RPO (Recovery Point Objective)**: 恢复点目标 - 可接受的数据丢失时间窗口
- **BCP (Business Continuity Plan)**: 业务连续性计划
- **DR (Disaster Recovery)**: 灾难恢复

## 🎯 1. RTO 和 RPO 目标

### 服务分类与优先级

| 服务类型             | RTO 目标 | RPO 目标 | 优先级    | 业务影响               |
| -------------------- | -------- | -------- | --------- | ---------------------- |
| **主网站 (7zi.com)** | 4 小时   | 15 分钟  | P0 (关键) | 直接影响用户访问和收入 |
| **数据库**           | 2 小时   | 5 分钟   | P0 (关键) | 核心数据存储           |
| **API 服务**         | 4 小时   | 15 分钟  | P0 (关键) | 后端服务依赖           |
| **测试环境 (bot5)**  | 24 小时  | 4 小时   | P2 (低)   | 不影响生产环境         |
| **监控告警**         | 1 小时   | N/A      | P1 (高)   | 需要快速发现问题       |
| **日志服务**         | 8 小时   | 1 小时   | P2 (低)   | 可暂时不可用           |

### RTO/RPO 说明

#### 主网站 (7zi.com)

- **RTO: 4 小时**
  - 理由: 从备份恢复 + 部署新实例 + DNS 切换时间
  - 优化方向: 自动化部署、预备用服务器
- **RPO: 15 分钟**
  - 理由: 基于 Litestream 实时复制 + 定期增量备份
  - 优化方向: 实时数据库复制、增加备份频率

#### 数据库

- **RTO: 2 小时**
  - 理由: 数据库恢复通常比应用恢复更快
  - 优化方向: 热备机、主从复制
- **RPO: 5 分钟**
  - 理由: 最小化数据丢失
  - 优化方向: 实时同步到备用节点

### 2.5 备份恢复流程

#### 场景 1: 数据库损坏

```bash
步骤:
  1. 停止应用服务
  2. 备份当前损坏的数据库
  3. 从最新备份恢复:
     ./scripts/backup-db.sh restore /opt/7zi/backups/7zi-db_20260329_020000.sqlite.gz
  4. 验证数据库完整性
  5. 启动应用服务
  6. 运行健康检查

预计时间: 30 分钟
```

#### 场景 2: 完全服务器故障

```bash
步骤:
  1. 在备用服务器上部署环境
  2. 从 S3 下载最新备份
  3. 恢复数据库
  4. 恢复配置文件
  5. 启动服务
  6. 切换 DNS 到新服务器
  7. 验证服务

预计时间: 3-4 小时
```

#### 场景 3: 误删除数据

```bash
步骤:
  1. 停止写入操作
  2. 从 S3 恢复到删除前的备份
  3. 使用 Litestream WAL 恢复到最近时间点
  4. 验证数据恢复
  5. 启动服务

预计时间: 1-2 小时
```

## 🔄 3. 服务故障切换流程

### 3.1 故障分类

| 故障类型         | 严重性 | 响应时间 | 切换策略            |
| ---------------- | ------ | -------- | ------------------- |
| **单服务器故障** | 高     | 15 分钟  | 自动重启 / 蓝绿切换 |
| **数据库损坏**   | 严重   | 30 分钟  | 恢复备份 / 切换从库 |
| **网络故障**     | 中     | 1 小时   | 切换备用线路        |
| **数据中心故障** | 严重   | 4 小时   | 跨区域切换          |
| **人为误操作**   | 高     | 2 小时   | 回滚 / 恢复备份     |
| **安全攻击**     | 严重   | 30 分钟  | 隔离 / 切换备用     |

### 3.3 跨服务器故障切换

**目标服务器**:

- **主站**: 7zi.com (165.99.43.61)
- **备用**: bot5.szspd.cn (182.43.36.134)

**切换流程**:

```bash
阶段 1: 准备 (15 分钟)
  1. 在备用服务器上部署最新代码
  2. 同步数据库备份
  3. 配置 SSL 证书
  4. 验证服务可用性

阶段 2: 切换 (30 分钟)
  1. 更新 DNS TTL (降低到 60 秒)
  2. 更新 DNS 记录指向备用服务器
  3. 等待 DNS 传播 (最大 5 分钟)
  4. 验证流量切换
  5. 监控服务指标

阶段 3: 稳定 (持续)
  1. 持续监控服务状态
  2. 收集错误日志
  3. 准备回滚方案

回滚流程 (如需要):
  1. 恢复 DNS 到主服务器
  2. 等待 DNS 传播
  3. 验证服务恢复
```

### 4.4 告警配置

**告警级别定义**:

- **Info**: 信息通知，无需立即处理
- **Warning**: 警告，需要关注，建议 4 小时内处理
- **Critical**: 严重，需要立即处理，建议 30 分钟内响应
- **Emergency**: 紧急，需要立即处理，建议 10 分钟内响应

**告警通道**:

1. **Telegram Bot** (主要)
   - 所有告警
   - 支持交互式操作
2. **Email** (备用)
   - Warning 及以上级别
   - 详细报告附件
3. **短信** (紧急)
   - Critical 及 Emergency 级别
   - 直接联系相关负责人

**告警抑制规则**:

- 同一问题 10 分钟内只发送一次告警
- 维护窗口期间抑制非紧急告警
- 自动恢复的通知延迟 5 分钟发送

## 🔐 8. 安全考虑

### 8.1 备份数据加密

**加密方式**:

- 数据库备份: gzip + AES-256-GCM
- 配置文件: Git-crypt / S3 服务端加密
- S3 存储: SSE-S3 (服务端加密)

**密钥管理**:

- 加密密钥存储: 硬件安全模块 (HSM) 或 KMS
- 密钥轮换: 每 90 天
- 密钥访问: 最小权限原则

### 8.2 访问控制

**备份访问权限**:

- 读取权限: 系统管理员 + 技术负责人
- 恢复权限: 系统管理员 + 事故指挥官
- 删除权限: 仅系统管理员

**监控访问权限**:

- 查看权限: 所有团队成员
- 配置权限: 系统管理员
- 告警配置: 系统管理员 + 技术负责人

### 8.3 数据隐私

**敏感数据处理**:

- 备份前脱敏敏感字段
- 测试环境使用匿名数据
- 符合 GDPR/CCPA 要求

**审计日志**:

- 记录所有备份/恢复操作
- 记录告警处理历史
- 定期审计访问日志
