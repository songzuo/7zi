# ADR-0002: 使用 Socket.IO 实现 WebSocket

## 状态

Accepted

## 上下文

项目需要实时通信功能，用于以下场景：

- AI Agent 实时状态同步
- 任务进度实时更新
- 多用户协作
- 实时通知

原始的 WebSocket API 需要手动处理：

- 连接管理（重连、心跳）
- 房间管理
- 消息序列化
- 跨浏览器兼容性

## 决策

采用 [Socket.IO](https://socket.io/) 作为 WebSocket 通信库。

### 实现方案

1. **服务端**: 使用 Socket.IO Server (Node.js)
2. **客户端**: 使用 Socket.IO Client
3. **协议**: WebSocket（降级到 HTTP Long Polling）
4. **适配器**: Redis Adapter（多服务器支持）

### Socket.IO 优势

- **自动重连**: 内置智能重连机制
- **房间管理**: 原生支持房间/命名空间
- **跨浏览器**: 自动降级，兼容性好
- **二进制支持**: 支持传输二进制数据
- **中间件**: 认证、日志等中间件支持
- **TypeScript**: 完整类型定义

## 权衡

### 替代方案 1: 原生 WebSocket API

**优点**:

- 原生支持，无额外依赖
- 轻量级
- 完全控制

**缺点**:

- 需要手动实现重连、心跳
- 需要手动处理房间管理
- 跨浏览器兼容性需处理

**选择 Socket.IO 的原因**: 项目需要房间管理和自动重连，Socket.IO 提供开箱即用的支持。

### 替代方案 2: Pusher

**优点**:

- 托管服务，无需管理服务器
- 可靠性好
- 全球边缘节点

**缺点**:

- 成本较高（按连接计费）
- 数据隐私顾虑
- 依赖第三方服务

**选择 Socket.IO 的原因**: 项目已有服务器基础设施，自建 WebSocket 服务成本更低。

### 替代方案 3: SockJS

**优点**:

- 良好的浏览器兼容性
- 降级机制完善

**缺点**:

- 维护较少
- 功能相对简单
- 不支持房间

**选择 Socket.IO 的原因**: Socket.IO 活跃维护，功能更丰富。

## 后果

### 正面影响

- ✅ **快速开发**: 房间、重连等开箱即用
- ✅ **可靠性**: 自动重连和降级机制
- ✅ **可扩展**: 支持多服务器集群（通过 Redis Adapter）
- ✅ **开发体验**: 事件驱动 API 简洁易用
- ✅ **类型安全**: 完整的 TypeScript 支持

### 负面影响

- ⚠️ **Bundle 体积**: Socket.IO Client 约 20KB gzipped
- ⚠️ **服务器资源**: 需要维护 Socket.IO 服务器

### 版本选择

使用 Socket.IO 4.8.3：

- 支持最新的 WebSocket 标准
- 性能优化（更小的包体积）
- 更好的错误处理
