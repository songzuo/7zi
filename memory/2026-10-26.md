## RBAC 权限判定 3 处真实缺陷（提交 fe4189b986）

RBAC 测试此前**整文件加载失败**（3 个文件 collect error），**从未真正跑过**。
修好加载之后暴露出 3 个真实的权限判定缺陷 —— 这类"测试没跑过所以缺陷藏着"
的情况值得警惕：

1. **条件字段解析不到 attributes**（engine.ts）
   `resource.status` 只在 resource 自身（resourceId/ownerId/teamId）上找，
   而 status/priority/title 在 resource.attributes 里 → undefined →
   条件恒不成立 → **所有带条件的权限都被判为不通过**。

2. **条件右值不支持跨对象引用**（engine.ts）
   `{ field: 'resource.ownerId', operator: EQUALS, value: 'user.userId' }`
   语义是「资源属主 == 当前用户」，但右值被当字面量，
   'user_1' === 'user.userId' 恒 false → **「只能读自己的资源」永远不成立**。

3. **角色追加权限不生效**（repository.ts）
   getUserPermissionContext 只读静态 DEFAULT_ROLE_DEFINITIONS，
   看不见 assignPermissionsToRole() 写进 role_permissions 表的记录 →
   **「给角色追加权限」这个动作完全无效**。

另修 4 处测试替身/测试问题：
- 全局 mock 逐个列举 permissions/repository 的导出（只有 4 个），
  其余一被调用就报 'No "xxx" export is defined' → 改 importActual 保留真实实现。
  **教训**：曾试过覆写 getUserRoles/hasPermission/hasRole 给固定值，
  但 hasPermission/hasRole 是纯函数（入参是权限上下文不是 DB），
  覆写成恒 true 会让权限判定测试全部失真 —— 替身要按"边界"划分，不是按"返回值方便"划分。
- mock db 的 CREATE TABLE 正则把 `IF NOT EXISTS` 的 IF 当成表名 → 表没建出来。
- mock db 补 RBAC 默认角色种子（真实环境 seed.ts 写入，mock 不跑种子）。
- 测试自身：import 路径 './types' → '../types'；跨用例依赖上一个用例的数据。

**验证**：permissions 3 files 加载失败 → **4 files / 84 tests 全绿 exit=0**；
`npx tsc --noEmit` exit=0。

**教训**：测试"文件加载失败"和"测试通过"一样要当回事 —— 前者更危险，
因为 CI 里常被忽略成"这个文件坏了"。移除 @ts-nocheck 往往会暴露这类问题。

## MCP 既有失败的真相：3 个失败里 2 个是真 bug（提交 e322653865）

T161 收尾时留了 3 个 MCP 既有失败（`src/lib/mcp/__tests__/enhancement.test.ts`）。
子代理用 git stash 对照确认"与本次改动无关"——这点没错，但**没查这些失败本身**。
我逐个查了源码历史，发现它们**从测试加入那天（04193799db, 3-31）起就没通过过**。

### 失败 1：closeStream 静默丢掉 close 事件（真 bug）
```ts
stream.state = 'closed'                                  // 先置 closed
await this.sendEvent(streamId, { event: 'close', ... })  // sendEvent 对 closed 抛 INVALID_STATE
catch { /* Stream might already be closed */ }            // 被静默吞掉
```
`sendEvent` 的状态闸门：`state === 'closed' | 'error'` → 抛 INVALID_STATE。
**自己置的状态挡住了自己要发的消息**，catch{} 又吞了 → 客户端永远收不到 close 事件，无任何日志。

### 失败 2：closeStream 立刻删流，"已关闭"状态无法观察（真 bug）
`cleanupStream()` 把流从 Map 删掉 → `getStream()` 立刻 undefined → `getStats().closed` 恒 0
→ `cleanupOldStreams()` 里 `state === 'closed'` 分支成**死代码**。
而 `cleanupOldStreams()` 本来就是为回收 closed 流设计的。
修复：closeStream 只标记状态+发事件，真正回收交给 ping 定时器调 cleanupOldStreams()。

### 失败 3：生命周期进度混进 progressHistory（契约不一致）
executeWithStreaming 自动上报「Starting X」(0%) 和「Completed X」(100%)，
这两条也进 progressHistory → 画进度条时业务 0%/100% 与生命周期 0%/100% 混淆，
可能出现"进度条倒退"。
修复：reportProgress 加 `record` 选项，生命周期事件 record:false（仍透给 onProgress）。

### 失败 4：reason 断言写死大小写（测试问题）
实现侧 reason 一律 Title Case，断言却 `toContain('insufficient')` 小写 → 改 `toMatch(/insufficient/i)`。

**验证**：vitest src/lib/mcp + src/lib/message-queue + src/app/api/workflow
→ **25 files / 222 tests 全绿** exit=0；tsc exit=0；eslint 0 error。

**教训**：
1. **"既有失败"不等于"不用管"**。子代理用 stash 对照证明"我没造成"是对的做法，
   但主管要接着问一句"**那它为什么一直挂**"——答案是挂了 7 个月。
2. **自己置的状态会挡住自己的动作**。这类"状态闸门 + 静默 catch"的组合，
   失败时**一点痕迹都不留**，只能靠读代码顺序发现。
3. **死代码是设计漏洞的信号**：`cleanupOldStreams` 里清理 closed 的分支不可达，
   说明"谁负责回收"这件事在重构中丢了。

## 【安全】A2A 5 个路由全部无鉴权（20:30 修复，提交 6dcd831b2）

T179 汇报时提到"剩余 4 个失败文件（a2a×3 + notifications）属 T178，
根因是 `@/lib/agent-scheduler/scheduler` 模块解析失败"。我接着查，
发现的不只是路径问题 —— **是一组真实的越权漏洞**。

### 漏洞
A2A 的 AgentCard 自己声明了 securitySchemes：
```json
"securitySchemes": { "bearerAuth": {...}, "apiKey": {...} }
```
extended agent card 里还明写「Administrative operations for authenticated users」。

但实现里**一个鉴权都没有**：
| 路由 | 匿名可做 |
|---|---|
| GET/POST /api/a2a/registry | 列出、注册 agent |
| GET/PUT/DELETE/PATCH /api/a2a/registry/[id] | 读、改名、**删除** agent |
| POST /api/a2a/registry/[id]/heartbeat | 上报心跳 |
| POST /api/a2a/jsonrpc | 取 extended agent card（含管理操作） |

仓库里**没有根 middleware.ts**（`src/middleware/` 下是 rate-limit/rbac/security/
tenant-guard 四个普通模块，不是 Next.js middleware）→ 没有全局兜底，
必须路由自己守门。

### 修复
新增 `src/lib/agents/a2a/auth.ts`：
- Bearer JWT → 复用 `@/lib/auth/service` 的 authenticateToken（与仓库既有做法一致）
- X-API-Key → 按 AgentCard 声明的 apiKey scheme 校验，
  合法值从 `A2A_API_KEY` / `A2A_API_KEYS` 环境变量读；
  **没配置就不接受任何 key**（避免"配置缺失等于放行"）
- `canAccessAgent()`：API Key 方式只能操作与自己匹配的 agent
- 5 个路由全部用 `withA2AAuth` 包起来

### 顺带修的
- **a2a×3 测试整份加载失败（挂了 7 个月）**：写于 3-29，
  import 的 `src/lib/agent-scheduler/` 在 **3-30**（c4bf2d327f）被移到
  `src/lib/agents/scheduler/`，生产代码改用 `@/lib/agents/a2a/agent-registry`。
  → 新增 `tests/api-integration/mocks/agent-scheduler-compat.ts`，
  把旧 API 映射到现在的 `getAgentRegistry()`，**断言语义一行未改**。
- **notifications.test.ts 语法错误**：两个 describe 少了闭合 `})`，
  文件根本不是合法 JS。补齐后 4 用例全过。

### 验证
`npx vitest run tests/api-integration` → **25 files / 222 tests 全绿** exit=0
（修复前 5 个文件加载失败 + 12 个文件失败 / 99 用例失败）

### 教训
1. **"模块解析失败"的测试任务，根因往往是架构变更而非笔误** ——
   顺着"这个模块去哪了"查，就能查出 3-30 那次目录搬迁，
   再顺着 A2A 路由的现状，就能查出越权漏洞。
2. **AgentCard 声明的 securitySchemes 是契约**。实现不兑现声明，
   等于对外承诺了保护但实际裸奔。查安全问题时，先看**声明**，
   再对**实现**。
3. **没有全局 middleware 时，每个路由都是自己的第一道防线** ——
   不能因为"别的路由有鉴权"就假设这个也有。
