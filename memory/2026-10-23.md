### 🐛 retry.ts 的 3 个真 Bug（历史遗留，非 T66 引入）

**1. 自定义 shouldRetry 不再被默认规则覆盖**（最严重）
原写法 `shouldRetry(...) || isRetryableError(...)`：
shouldRetry 返回 false 时，会被默认规则救回 —— 而 `'Error'` 就在
`DEFAULT_RETRYABLE_ERRORS` 里，所以**「自定义为不可重试」彻底失效**。
修复：shouldRetry 存在时**独占**判定权（withRetry + withRetrySync 两处同修）。

**2. @retry 装饰器泄漏内部 RetryResult**
装饰后的方法返回的是 `{success, data, attempts, totalTime}` 而不是原方法
的返回值 —— 被装饰方法的签名被静默改变。修复：保持原返回类型，
失败时抛出最后一次错误。

**3. logger mock 路径错误**
测试里 `vi.mock('../logger')` 从 `__tests__/` 解析到
`src/lib/error-reporting/logger`（不存在），mock 落空。应为 `'../../logger'`。

### ⏱ 测试超时根因
`vi.useFakeTimers()` + 直接 `await withRetry(...)`（不推进时钟）
→ 假时钟冻结 `setTimeout` → 每个用例挂到 12s testTimeout
→ 整文件 **246s**。改用真实时钟 + 极小 initialDelay(10~100ms)。

### 🐛 挖出一个真实 Bug
`src/app/api/analytics/trend/route.ts` 原代码：
```ts
const trendData = await getTrendData({ userId, timeRange }, timeRange)
```
但 `getTrendData` 的签名是 `(type: TrendType, timeRange: TimeRange)` ——
**第一个形参是趋势类型，不是过滤对象**。后果：
- `type` 被塞进了整个对象，永远匹配不上任何分支 → 趋势类型失效
- `userId` 过滤被**静默丢弃** → 越权读取他人趋势数据

现改为 `getTrendData(type, timeRange)` + 独立的 `getCurrentUserId()` 用户作用域，
与同目录其它 5 个 analytics 路由写法一致。**这是数据越权，值得单列。**
