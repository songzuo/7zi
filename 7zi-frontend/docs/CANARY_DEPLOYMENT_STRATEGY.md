## 🚀 部署策略选择

### 1. 灰度发布 (Canary) - **推荐用于生产环境**

#### 适用场景
- ✅ 生产环境首次发布
- ✅ 用户量大（>1000 DAU）
- ✅ 关键业务功能更新
- ✅ 需要真实用户验证

#### 流量分配策略

| 阶段 | 流量比例 | 持续时间 | 监控重点 |
|------|----------|----------|----------|
| **阶段 1** | 5% | 30 分钟 | 错误率、响应时间 |
| **阶段 2** | 15% | 30 分钟 | 用户反馈、转化率 |
| **阶段 3** | 50% | 60 分钟 | 系统稳定性、资源使用 |
| **阶段 4** | 100% | - | 全量发布 |

#### 流量分配维度

**1. 用户比例（默认）**
```bash
# 按用户 ID 哈希分配
split_clients "${remote_addr}" $canary_backend {
    10%    "http://canary:3001";
    "*"    "http://stable:3000";
}
```

**2. 地区维度**
```bash
# 按地理位置分配
# 示例：先在特定地区验证
map $geoip_country_code $canary_backend {
    default      "stable";
    "US"         "canary";  # 美国用户先体验
    "CN"         "stable";  # 中国用户稍后
}
```

**3. 用户组维度**
```bash
# 按 Cookie 或 Header 分配
# 示例：内部用户、Beta 用户优先
map $cookie_user_group $canary_backend {
    default      "stable";
    "beta"       "canary";
    "internal"   "canary";
}
```

#### 执行命令
```bash
# 标准灰度发布（初始 10%，持续 30 分钟）
./scripts/deploy/deploy.sh canary ghcr.io/.../7zi-frontend:v1.5.0 10 30

# 保守策略（初始 5%，持续 60 分钟）
./scripts/deploy/deploy.sh canary ghcr.io/.../7zi-frontend:v1.5.0 5 60

# 激进策略（初始 20%，持续 15 分钟）
./scripts/deploy/deploy.sh canary ghcr.io/.../7zi-frontend:v1.5.0 20 15
```

### 2. 蓝绿部署 (Blue-Green)

#### 适用场景
- ✅ 紧急热修复
- ✅ 回滚后重新部署
- ✅ 小型应用（<500 DAU）
- ✅ 需要快速切换

#### 流程
```
┌─────────┐        ┌─────────┐
│  Blue   │  ────> │  Green  │
│ (当前)  │        │ (新版本)│
│  100%   │        │   0%    │
└─────────┘        └─────────┘
     │                  │
     └────[一键切换]────┘
            (秒级)
```

#### 执行命令
```bash
# 蓝绿部署
./scripts/deploy/deploy.sh blue-green ghcr.io/.../7zi-frontend:v1.5.0
```

## 📊 监控指标

### 关键指标 (KPI)

#### 1. 错误率
- **阈值**: < 5%
- **告警**: > 5% 持续 5 分钟
- **回滚触发**: > 10% 立即回滚

#### 2. 响应时间 (P95)
- **阈值**: < 2000ms
- **告警**: > 2000ms 持续 5 分钟
- **回滚触发**: > 5000ms 立即回滚

#### 3. CPU 使用率
- **阈值**: < 80%
- **告警**: > 80% 持续 10 分钟
- **回滚触发**: > 95% 立即回滚

#### 4. 内存使用率
- **阈值**: < 85%
- **告警**: > 85% 持续 10 分钟
- **回滚触发**: > 95% 立即回滚

#### 5. 磁盘使用率
- **阈值**: < 90%
- **告警**: > 90% 持续 1 小时
- **回滚触发**: > 95% 清理后仍高则回滚

### 监控数据源

| 数据源 | 指标 | 收集频率 |
|--------|------|----------|
| **Nginx 日志** | 请求量、错误率、响应时间 | 实时 |
| **Docker Stats** | CPU、内存、网络 | 10秒 |
| **应用 API** | 健康状态、自定义指标 | 30秒 |
| **系统监控** | 负载、连接数、磁盘 | 1分钟 |

### 监控命令


## 🔄 回滚机制

### 自动回滚条件

| 指标 | 阈值 | 延迟 |
|------|------|------|
| 错误率 | > 10% | 立即 |
| 响应时间 | > 5000ms | 5 分钟 |
| 健康检查失败 | 3 次连续失败 | 立即 |
| 容器崩溃 | 重启失败 | 立即 |

### 手动回滚

#### 1. 标准回滚（推荐）
```bash
# 回滚到上一个版本
./scripts/deploy/rollback.sh

# 强制回滚（跳过确认）
./scripts/deploy/rollback.sh --force
```

#### 2. 指定版本回滚
```bash
# 回滚到指定镜像
docker stop 7zi-frontend
docker rm 7zi-frontend
docker run -d \
  --name 7zi-frontend \
  --restart unless-stopped \
  -p 3000:3000 \
  --env-file /root/.env.production \
  ghcr.io/.../7zi-frontend:v1.4.9
```

#### 3. 紧急回滚（最快）
```bash
# 切换流量到备份容器
docker start 7zi-frontend-backup
# 更新 Nginx 指向备份端口
systemctl reload nginx
```

### 回滚验证

```bash
# 验证回滚是否成功
curl -f https://7zi.com/api/health

# 检查容器状态
docker ps | grep 7zi-frontend

# 查看应用版本
curl https://7zi.com/api/version
```

| **周二-周四** | 常规发布 | 避开周末，团队在线 |

## 📝 发布流程

### 1. 发布前（T-1 小时）

```bash
# 1. 确认镜像版本
docker images | grep 7zi-frontend

# 2. 备份数据库
mysqldump -u root -p 7zi_db > backup_$(date +%Y%m%d).sql

# 3. 检查系统状态

free -h
df -h

# 4. 预热 CDN（如需要）
```

```bash

./scripts/deploy/collect-metrics.sh 300

tail -f /var/log/nginx/7zi.access.log
```

```bash

watch -n 10 'docker stats --no-stream | grep 7zi'
```
